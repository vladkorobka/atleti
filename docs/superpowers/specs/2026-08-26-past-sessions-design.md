# Ретроактивний запис проведених занять

Дата: 2026-08-26

## Проблема

Тренер провів заняття 20 серпня, але не записав його в календар. Заняття з балансу
клієнта не списалось, і виправити це неможливо: `POST /api/coach/sessions` відхиляє
будь-яку дату в минулому (`apps/web/app/api/coach/sessions/route.ts`, перевірка
`start <= new Date()` → 400 «Дата заняття має бути в майбутньому»), а `DatePicker`
у модалці «Нове заняття» має `min={kyivDateInput(new Date())}`.

Зміна статусу вже наявного заняття (в тому числі минулого) працює і не потребує
доопрацювання: `PUT /api/coach/sessions/[sessionId]` дозволяє перехід у будь-який
бік і коригує `Balance.sessionsUsed` на ±1, не даючи піти нижче нуля.

## Рішення

Дозволити створення заняття минулою датою одразу зі статусом `completed`, зі
списанням балансу в тій самій операції.

> **Статус:** реалізовано в гілці `feature/past-sessions`. Документ оновлено після
> чотирьох раундів рев'ю — розділ «Що змінилось проти початкового плану» описує
> відхилення.

### Рішення, ухвалені під час брейнштормінгу

1. **UX** — та сама модалка «Нове заняття», без окремої кнопки. Коли обрана
   дата/час у минулому, модалка перемикається в режим ретроактивного запису.
2. **Баланс** — дозволяємо піти в мінус (заняття вже відбулось у реальності), але
   з підтвердженням через `ConfirmDialog`.
3. **Валідація** — для минулого пропускаємо перевірку робочого графіка й блоків
   (графік міг змінитись, заняття могло бути позаплановим), але лишаємо перевірку
   збігів у часі, щоб не записати одне заняття двічі.
4. **Статус** — для минулого доступний лише `completed`. Скасування тренером у цій
   кодовій базі реалізоване як `DELETE` із поверненням балансу, а не як статус
   `cancelled`, тож ретроактивне «скасовано» не має сенсу.

### Відхилені альтернативи

- **Окремий ендпоінт `POST /api/coach/sessions/past`** — дублює auth, перевірку
  `ClientCoach` і логіку збігів заради однієї гілки `if`.
- **Прибрати заборону минулого і покластися на `settlePastSessions`** — лінивий
  settle сам перевів би `scheduled` у минулому в `completed` зі списанням.
  Найменше коду, але списання балансу стає неявним побічним ефектом читання, і між
  створенням та наступним GET заняття виглядає як «Заплановано» в минулому.

## Зміни

### 1. `apps/web/lib/validations/coach.ts`

`sessionCreateSchema` отримує поле:

```ts
status: z.enum(['scheduled', 'completed']).optional().default('scheduled')
```

### 2. `apps/web/app/api/coach/sessions/route.ts` — `POST`

Поточна перевірка `if (start <= new Date())` замінюється на розгалуження за
`isPast = start <= new Date()`.

**Узгодженість дати й статусу:**

- `isPast && status !== 'completed'` → 400, «Заняття в минулому можна записати
  лише як проведене».
- `!isPast && status === 'completed'` → 400, «Майбутнє заняття не можна одразу
  позначити проведеним».

**Графік і блоки:** `checkWithinSchedule` викликається лише коли `!isPast`.

**Збіги в часі:** виконується для обох випадків через наявний
`hasBlockingConflict`. Для минулого вибірка кандидатів розширюється:
`status: { $in: ['scheduled', 'completed'] }` замість лише `'scheduled'` —
інакше вже проведене заняття в тому ж слоті не було б помічене. Правило
«Спліт поверх Спліт» лишається без змін. Конфлікт → 409.

**Баланс:**

- `!isPast` — без змін: якщо `sessionsUsed + reserved >= sessionsTotal` → 402.
- `isPast` — перевірка балансу не блокує. Сесія створюється зі
  `status: 'completed'`, після чого `Balance.updateOne(..., { $inc: { sessionsUsed: 1 } })`.
  Баланс може стати від'ємним (`sessionsRemaining < 0`) — це очікувано.

Порядок: створення сесії, потім інкремент балансу — так само, як у `PUT` і
`settlePastSessions`.

### 3. `apps/web/app/coach/calendar/CalendarClient.tsx` — модалка «Нове заняття»

- З `DatePicker` знімається `min={kyivDateInput(new Date())}`.
- Обчислюється `isPastForm` — чи `kyivInputToUtc(form.date, form.time)` <= `new Date()`.
  Якщо час ще не обраний, минулим вважається дата, раніша за сьогоднішню.
- Коли `isPastForm`:
  - `TimePicker` рендериться без `hoursForDate(form.date)` — робочі години не
    обмежують ретроактивний запис.
  - Показується підказка: «Дата в минулому. Заняття буде записане як проведене,
    з балансу клієнта спишеться 1 заняття.»
  - Кнопка submit має підпис «Записати проведене».
  - Блокування за `selectedClientNoBalance` не застосовується.
  - У тілі запиту передається `status: 'completed'`.
- Коли `isPastForm && selectedClientNoBalance`, submit не відправляє запит одразу,
  а відкриває `ConfirmDialog`: «У клієнта немає вільних занять на балансі. Баланс
  піде в мінус. Продовжити?» Підтвердження виконує той самий запит.

### 4. `apps/web/app/coach/calendar/CalendarClient.tsx` — видимість занять поза графіком

Без цієї зміни ретроактивне заняття, записане на час поза робочими годинами або в
день, що зараз вихідний, не видно в UI взагалі: `buildDayTimeline` повертає `[]`
при відсутності `workingHours[dowKey]`, а заняття потрапляє в рядок слота лише коли
його час точно збігається з початком слота.

- `buildDayTimeline` після побудови слотів додає рядки для занять дня, які не
  потрапили в жоден слот. Такий рядок показує реальний час заняття і позначку
  «поза графіком»; кнопки «ред.» / «статус» / бейдж статусу — ті самі, що й у
  звичайному рядку.
- Панель дня рендерить ці рядки навіть коли `timeline` порожній (невибочий день),
  замість самого лише тексту «Не робочий день».

### 5. Без змін

- `PUT /api/coach/sessions/[sessionId]` — зміна статусу вже працює для минулих
  занять і коригує баланс.
- `PATCH` — редагування часу/тривалості лишається доступним лише для `scheduled`.
  Виправлення помилково записаного минулого заняття робиться через `DELETE`
  (повертає списане заняття на баланс) і повторний запис.
- `settlePastSessions` — не зачіпається; для сесії, створеної одразу як
  `completed`, він є no-op.

## Тести

Vitest, у наявні файли.

`apps/web/__tests__/api/coach/sessions.test.ts`:

- створення минулою датою зі `status: 'completed'` → 201, сесія має
  `status: 'completed'`, `sessionsUsed` збільшився на 1, у `transactions` з'явився
  запис `debit` із датою заняття і `recordedBy`;
- межа «рівно зараз» (через `vi.useFakeTimers({ toFake: ['Date'] })`);
- глибше за `MAX_BACKDATE_DAYS` → 400; у межах → 201;
- інваріант `sessionsUsed == count(status: 'completed')` через ланцюжок
  `POST(минуле) → settle → settle → PUT → settle → DELETE`;
- два заняття одного клієнта в один момент → 409 навіть для типу `split`;
- `PATCH` перенесення на час із проведеним заняттям того ж клієнта → 409, не 500;
- бронювання клієнтом слоту, зайнятого проведеним заняттям → 409, не 500;
- минула дата зі `status: 'scheduled'` (або без поля) → 400;
- майбутня дата зі `status: 'completed'` → 400;
- минуле заняття при нульовому балансі → 201, `sessionsRemaining` = −1;
- минуле заняття, що перетинається з уже проведеним у той самий час → 409;
- два минулі Спліт-заняття в той самий час → обидва 201;
- минуле заняття поза робочими годинами / у невибочий день → 201 (графік не
  перевіряється);
- майбутнє заняття — наявна поведінка (графік, збіги, 402 при нульовому балансі)
  не змінилась.

Наявні тести, що очікують 400 «Дата заняття має бути в майбутньому» для минулої
дати, оновлюються під новий контракт.

**E2E не додається.** Наявний набір у `apps/web/e2e/` неробочий і не чиниться в
межах цієї задачі: хелпери реєстрації створюють `PendingUser` замість `User` (акаунт
з'являється лише після підтвердження пошти), тести ходять на `/calendar` і `/clients`
замість `/coach/*`, а взаємодія написана під `input[type="date"]` і `<select>`, яких
більше немає — `DatePicker`, `TimePicker` і `Select` реалізовані на `<button>`.
Воскресіння набору — окрема задача; для неї знадобиться тестова база, бо зараз
налаштований лише продакшн-Atlas.

## Що змінилось проти початкового плану

Виявлено рев'ю, ухвалено після реалізації.

**Нижня межа минулого — `MAX_BACKDATE_DAYS = 365`** (`apps/web/lib/session-conflict.ts`).
Спека межі не мала; без неї описка в році давала 201 і тихе списання, а заняття
осідало в місяці, куди тренер уже не долистає. Константа спільна для серверної
перевірки і для `min` у `DatePicker`, причому клієнтська межа на добу суворіша —
сервер рахує з точністю до мілісекунди, пікер до доби.

**Унікальний індекс `uniq_coach_client_slot`** на `{coachId, clientId, scheduledAt}`,
partial для `status ∈ ['scheduled','completed']` (`packages/db/src/schemas/session.schema.ts`).
Перевірка збігів у роуті — це read-then-write, тож два одночасні POST створювали
дубль із подвійним списанням. Індекс закриває гонку на рівні БД. Скасовані заняття
виключені: після скасування слот можна зайняти знову. Спліт не постраждав — це
заняття різних клієнтів. `E11000` обробляється як 409 у трьох місцях: `POST` і
`PATCH` тренера та `POST` бронювання клієнта.

Перед створенням індексу базу перевірено скриптом
`packages/db/scripts/check-session-duplicates.mjs` — 21 заняття, 0 дублікатів.
Скрипт лише читає; його варто прогнати ще раз перед деплоєм на випадок, якщо
дублікати з'являться до релізу.

**Атомарність `PUT`.** `findOneAndUpdate` отримав у фільтр `status: before.status`.
Без цього між читанням `before` і записом статус міг змінити `settlePastSessions`,
і баланс коригувався за дельтою, якої вже не було — списання подвоювалось. При
розбіжності повертається 409.

**Компенсація при збої списання.** Якщо `Balance.updateOne` падає після
`Session.create`, сесія видаляється. Проведене заняття без списання не звірив би
ніхто: `settlePastSessions` дивиться лише на `scheduled`.

**`upsert: true` при списанні.** У клієнта без жодного поповнення документа
`Balance` ще немає — без `upsert` списання тихо зникало б.

**Борг видно клієнту.** `sessionsDebt = max(0, sessionsUsed − sessionsTotal)` у
`/api/client/balance`, плюс рядок «Заборговано: N» на дашборді й екрані балансу.
Головне число лишається клемпнутим у 0. Без цього клієнт після поповнення на 1
заняття знову бачив би 0 без пояснення.

**Журнал списань.** Ретроактивне списання пише `{type:'debit', sessions:1, note,
recordedBy}` у `Balance.transactions`. Це єдине списання, яке тренер робить вручну
заднім числом і якого клієнт не бачив у своєму розкладі. Свідома асиметрія:
`settlePastSessions`, `PUT` і `DELETE` журнал не пишуть — приведення всіх шляхів
до журналу виходить за межі цієї задачі.

**Попередження про мінус рахується за `paidLeft`, не за `remaining`.**
`coach/calendar/page.tsx` віддає обидва: `remaining = total − used − reserved` для
планування наперед і `paidLeft = total − used` для ретроактивного списання, яке
резерв не зачіпає. За `remaining` діалог спрацьовував би на клієнті з повним
пакетом і запланованими заняттями. Резерв у попередженні свідомо не враховується:
запис заднім числом може зробити вже заплановане заняття неоплаченим, і про це
тренер не попереджається.

**Обмеження часу в модалці.** Минулий день — без обмежень; сьогодні — верхня межа
`max(кінець графіку, поточний час)`, щоб заняття, проведене сьогодні о 19:00 при
графіку до 18:00, можна було записати; майбутній день — робочі години.

**«Повернути в заплановані» приховано для минулих занять.** Стан «минуле +
scheduled» недосяжний: `settlePastSessions` на першому ж читанні поверне заняття
в `completed`. Дія мовчки відкочувалась би.

**`GlassModal` — лічильник вкладеності.** Модалки вкладаються (`ConfirmDialog`
поверх форми), і кожна зберігала стиль `body` «до себе». Внутрішня запам'ятовувала
вже заблокований `overflow` і при закритті повертала його — сторінка лишалась без
скролу. Знімок тепер робить лише найзовнішня.
