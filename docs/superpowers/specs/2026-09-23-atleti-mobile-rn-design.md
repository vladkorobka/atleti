# Мобільні додатки на React Native

Дата: 2026-09-23
Гілка: `feature/mobile-rn`
Точка повернення до чистого вебу: тег `web-v1.0-pre-mobile` (коміт `28848a2`)

## Мета

Випустити мобільні додатки Атлеті для Android та iOS. Головна причина — **пуш-сповіщення**:
нагадування про заняття для клієнтів, повідомлення про записи й скасування для тренера.
Веб уже Mobile First і в телефоні працює, але надсилати пуші не вміє (на iOS — практично
взагалі). Додатково важать присутність у сторах, офлайн-перегляд і швидкість.

Порядок ролей: спершу тренерська, далі клієнтська.

## Що перевикористовується

| Частина | Реюз | Чому |
|---|---|---|
| `packages/types` (154 рядки, нуль залежностей) | 100% | чистий TypeScript |
| `apps/web/lib`: `tz`, `slot-utils`, `session-conflict`, `coach-schedule`, `balance`, `session-utils` | 100% | перевірено — жодного серверного імпорту |
| `apps/web/lib/validations` | 100% | залежність лише `zod` |
| 23 API-роути | ~95% | уже віддають JSON; змінюється тільки auth-рядок |
| `packages/db` | 100%, **тільки сервер** | Mongoose = Node, у RN не імпортується ніколи |
| `packages/ui` (18 компонентів) | 0% | `div` + Tailwind |
| 17 сторінок, з них 9 — Server Components | 0% | RSC у RN не існує |

## Рішення, ухвалені під час брейнштормінгу

1. **Один додаток, дві ролі** — як у вебі. Роль із токена визначає навігацію. Одна
   збірка, одна сторінка в кожному сторі, одне ревʼю Apple. Клієнтська частина у фазі 2
   додається в уже працюючий додаток, а не починається з нуля.
2. **Повний паритет тренерського додатка з вебом** — усі 5 екранів, включно з робочим
   графіком, блоками, балансом і анамнезом.
3. **Офлайн — тільки читання.** Черги мутацій немає: без мережі форми не відкриваються.
4. **Вхід — email/пароль**, як зараз. Google лишається закоментованим і у вебі, і в мобілці.
5. **Дизайн — Glass усюди, натив для вводу.** Візуально той самий Атлеті; дата, час,
   списки вибору й алерти — системні.
6. **Нагадування — локальні сповіщення на пристрої**, без серверного cron.
7. **Клієнт налаштовує одне нагадування** (1–24 год) з можливістю вимкнути.
   Тренер натомість отримує **один ранковий дайджест**.
8. **Серійні пуші згортаються** через `collapseId`/`tag` без затримки й планувальника.
9. **Центр сповіщень** — стрічка подій із терміном життя місяць, у мобілці **і у вебі**.
10. **Уся розробка й приймання — в Expo Go.** Платежі Apple і Google відкладені до того, як
    замовник прийме додаток. Віддалені пуші в Expo Go не працюють, тож їхня перевірка на
    живому пристрої свідомо відкладається — код пишеться й покривається юніт-тестами проти
    dev-режиму. Локальні нагадування й центр сповіщень перевіряються повноцінно.

## Відхилені альтернативи

- **PWA + Capacitor** — загорнути наявну Next.js-збірку. Швидше в рази, але слабкі пуші,
  гірша плавність і ризик відмови на ревʼю App Store за «сайт в обгортці».
- **Два окремі додатки** («Атлеті Тренер» і «Атлеті») — подвоює конфігурації EAS, процеси
  ревʼю, код входу й пушів. Виправдано, коли аудиторії — різні продукти; тут вони працюють
  з тими самими заняттями.
- **Окремий репозиторій** — типи довелося б дублювати або публікувати пакетом, зміна API
  стала б двома PR. `pnpm-workspace.yaml` уже глобить `apps/*`, монорепо не опирається.
- **`packages/ui-native`** — пакет без другого споживача. Додаток один і назавжди один,
  тож мобільні компоненти живуть у `apps/mobile/components/`.
- **Серверний cron для нагадувань** — Vercel Cron на безкоштовному тарифі запускається раз
  на добу; для «за годину» потрібен Pro за $20/міс. Крім того, зробив би персональний час
  нагадування дорогим: запит на кожне з 24 можливих значень або обчислюване поле `remindAt`.
- **Згортання пушів із затримкою** — відкладена відправка потребує планувальника, тобто
  того самого cron. Плюс будь-яке фіксоване вікно або рве серію, або змушує чекати.
- **Redux / Zustand** — майже весь стан серверний, його тримає TanStack Query.

## 1. Структура монорепо

```
apps/
  web/           — UI без змін; змінюється лише auth-рядок у роутах + дзвіночок у шапці
  mobile/        — НОВИЙ: Expo Router, один додаток, дві ролі
packages/
  types/         — як є
  db/            — як є, тільки сервер
  ui/            — веб-компоненти, як є
  core/          — НОВИЙ: уся чиста доменна логіка
  api-client/    — НОВИЙ: типізовані виклики до /api
```

### `packages/core`

Переїжджають з `apps/web/lib` (усі перевірені на чистоту — жодного серверного імпорту):

`tz.ts` · `slot-utils.ts` · `session-conflict.ts` · `coach-schedule.ts` · `balance.ts` ·
`session-utils.ts` · `validations/client.ts` · `validations/coach.ts`

Разом із ними переїжджають шість тестів з `apps/web/__tests__/lib/` і лишаються на Vitest —
саме вони доводять, що перенесення нічого не зламало.

У `apps/web/lib` лишається все, що торкається БД: `auth`, `db`, `email`, `settle-sessions`,
`coach-utils`, `middleware-utils`, `email-templates`.

### `packages/api-client`

Обіцяний у CLAUDE.md, але відсутній у коді. Типізовані виклики, підстановка `Authorization`,
єдиний формат помилок, обробка 401 з оновленням токена. Нічого не кешує й не знає про React.

У цій фазі веб на нього **не** переводиться — щоб не чіпати робочий календар.

### `apps/mobile`

```
app/                   — Expo Router
  (auth)/login
  (coach)/_layout      — вкладки: головна, клієнти, календар, профіль
  (client)/            — порожньо до фази 2
components/            — Glass-компоненти на View/Text
lib/                   — api, сховище токенів, пуші, Query
```

### Ризики етапу

- **Рух робочого коду.** Винесення `packages/core` чіпає веб. Окремим комітом, до будь-якого
  мобільного коду, з `pnpm test` і `pnpm typecheck` як доказом.
- **Metro й pnpm.** `.npmrc` немає, тобто symlink-розкладка, з якою Metro історично воює.
  Лікується `node-linker=hoisted`, але це змінює `node_modules` для всього монорепо.
  Перевірка: `pnpm install` → `pnpm build` → `pnpm test` **до** появи Expo.

## 2. Автентифікація

### Проблема

`session: { strategy: 'jwt' }` у `apps/web/lib/auth.config.ts` — це добре, але NextAuth
віддає JWT у httpOnly-cookie, а всі 23 роути читають його через `await auth()`.
React Native браузерної cookie-сесії не має.

### Подвійний хелпер

`apps/web/lib/api-auth.ts`:

```ts
getAuthUser(req): Promise<AtletiSession | null>
```

Є `Authorization: Bearer …` — перевіряємо наш токен через `jose`; немає — падаємо назад на
`await auth()`. Повертає **той самий** `AtletiSession`. У роутах міняється один рядок, тіло
не чіпається. Веб продовжує працювати на cookie й змін не помічає.

Зміна механічна, але наскрізна — 23 файли, окремим комітом із прогоном роутових тестів.

### Токени

- **Access** — підписаний JWT, 15 хвилин, claims ті самі, що кладе NextAuth: `userId`,
  `role`, `nickname`, `emailVerified`. Підпис через `jose` на наявному `NEXTAUTH_SECRET`.
  `jose@6.2.3` уже в дереві транзитивно — додається **явною** залежністю.
- **Refresh** — непрозорий випадковий рядок, 60 днів, у базі лише sha256-хеш (патерн
  `resetTokenHash` з `user.schema.ts`). Ротація при кожному використанні. Повторне
  використання = ознака крадіжки → гасимо сесію пристрою.

На пристрої обидва в `expo-secure-store` (Keychain / Keystore).

### `Device` — одна колекція замість двох

`packages/db/src/schemas/device.schema.ts`

```
userId            ObjectId → User
refreshTokenHash  sha256, унікальний індекс
expiresAt         TTL-індекс
expoPushToken     може бути порожнім
platform          ios | android
lastSeenAt        для діагностики
```

Сесія й push-токен мають той самий життєвий цикл: з'являються при вході, зникають при
виході, належать конкретній інсталяції. Тому один документ = один телефон. Вихід видаляє
документ і разом із сесією автоматично відписує пристрій від пушів. Кілька пристроїв на
користувача працюють самі собою. TTL прибирає сміття без cron.

### Нові роути

```
POST /api/mobile/auth/login     — bcrypt-перевірка як в auth.ts; віддає пару + профіль, створює Device
POST /api/mobile/auth/refresh   — обмін refresh на нову пару
POST /api/mobile/auth/logout    — видаляє Device
```

Реєстрація, підтвердження пошти й скидання паролю беруться з наявних роутів — вони й зараз
не вимагають сесії.

### Чого не робимо

NextAuth у вебі не чіпаємо. Веб на cookie, мобілка на Bearer, спільний у них лише
`getAuthUser` і формат claims.

## 3. Пуш-сповіщення

Інфраструктури немає жодної: ні зберігання токенів, ні моделі сповіщень, ні `vercel.json`,
ні cron. Єдиний вихідний канал — email через Resend.

### Каталог подій

| Подія | Роут | Кому | Фаза |
|---|---|---|---|
| Клієнт забронював | `POST /api/client/sessions` | тренеру | **1** |
| Клієнт скасував | `DELETE /api/client/sessions/[id]` | тренеру | **1** |
| Тренер створив | `POST /api/coach/sessions` | клієнту | 2 |
| Тренер переніс | `PUT /api/coach/sessions/[id]` | клієнту | 2 |
| Тренер змінив статус | `PATCH /api/coach/sessions/[id]` | клієнту | 2 |
| Тренер скасував | `DELETE /api/coach/sessions/[id]` | клієнту | 2 |
| Запрошення клієнта | `POST /api/coach/clients/invite` | клієнту | 2 |
| Поповнення балансу | `POST /api/coach/clients/[id]/balance` | клієнту | 2 |

Код відправки пишеться одразу для всіх восьми — він однаковий, а тримати його наполовину
написаним півроку гірше.

### Шар відправки

`apps/web/lib/push.ts` — дзеркало `lib/email.ts`, аж до поведінки в dev (немає ключа → лог
у консоль, не падаємо). Бере всі `Device` з непорожнім `expoPushToken`, шле пачкою в Expo
Push Service (безкоштовний, бере на себе APNs і FCM; сертифікати генерує EAS).

Токени з відповіддю `DeviceNotRegistered` видаляються з бази.

**Відправка ніколи не валить запит** — пуш це побічний ефект, а не частина транзакції.

### Згортання серій

Проблема: тренер планує 12 занять — клієнт отримує 12 пушів. Затримка з групуванням не
підходить (потребує планувальника; будь-яке вікно або рве серію, або змушує чекати).

Рішення — **заміна замість затримки**. Пуші йдуть негайно, кожен окремо, але з однаковим
`collapseId` (iOS) і `tag` (Android), обидва `sessions-added-<userId>`. Телефон показує
одне сповіщення, текст якого оновлюється.

> Деталь із документації Expo: на Android `collapseId` згортає лише повідомлення **в дорозі**,
> а вже показане замінює `tag`. Тому ставимо обидва.

Щоб телефон не дзижчав 12 разів: поле `sound` не вказується → сповіщення беззвучне. Перший
пуш у серії йде зі звуком, решта — мовчки.

Лічильник для тексту не зберігається, а запитується: скільки занять створено цьому
користувачеві за останню годину. Для цього `SessionSchema` отримує `{ timestamps: true }`
(зараз його немає). Міграція не потрібна — наявні заняття лишаться без `createdAt` і в
запит «за останню годину» не потраплять.

Година тут — **рамка запиту, а не очікування**: пуш іде миттєво завжди.

### Нагадування — локальні, без cron

`expo-notifications` планує сповіщення на конкретний час без сервера. Додаток при
синхронізації календаря вже знає майбутні заняття й розставляє нагадування сам.

Актуалізація вже існує: кожна зміна розкладу породжує подієвий пуш із таблиці вище →
додаток тягне свіжий розклад → стирає старі заплановані нагадування → ставить нові.
Плюс перепланування при кожному відкритті додатка.

**Налаштування клієнта.** У `user.schema.ts` одне поле:

```
reminderHours: { type: Number, default: 24 }   // null — нагадування вимкнені
```

Одне поле замість пари «тогл + число», бо пара рано чи пізно розсинхронізується. Тогл у меню
пише `null` або повертає число. Значення 1–24. Читається скрізь через `?? 24`, бо Mongoose
ставить `default` лише при створенні документа, і наявні користувачі матимуть `undefined`.
Масова міграція не робиться.

Поле додається у наявні `GET`/`PUT /api/user/profile`. У вебі налаштування **не показується** —
веб нагадувань не шле.

**Тренер нагадувань на кожне заняття не отримує.** Замість них — один ранковий дайджест
(«сьогодні 6 занять, перше о 9:00»).

### Ліміт iOS

64 **одночасно очікуваних** локальних сповіщення на додаток. Серверні пуші в ліміт не входять —
вони доставляються, а не чекають. Черга сама спорожнюється: спрацювало — звільнило місце.

- Клієнт: 3 заняття на тиждень × 1 нагадування = 3 очікуваних. Впертися неможливо.
- Тренер: дайджест = 1 на добу. Проблема зникає, а не лікується.

Ковзне вікно тримається на тому, що додаток регулярно відкривають. Фонове пробудження на iOS
(`content-available`) не дає стовідсоткової гарантії — система вирішує сама.

### Дозволи

Запит на сповіщення — **після першого входу**, на екрані з поясненням «Повідомимо, коли клієнт
запишеться або скасує заняття», а не при першому запуску. Відмовився — додаток працює, в
профілі є перемикач. На iOS відмову не можна перепитати системно, тільки відправити в
Налаштування, тож перший показ має значення.

## 4. Шар даних, кеш і офлайн

Три рівні: `packages/api-client` (запит → дані або помилка) → TanStack Query (кеш, повтори,
фонове оновлення) → persist-шар на диск.

Query замінює те, що у вебі роблять Server Components: 9 сторінок зараз тягнуть дані на
сервері, у мобілці їх тягне клієнт.

### Оновлення токена й гонка

Access живе 15 хвилин, тож 401 — нормальний робочий стан. Перехоплення в `api-client`:
401 → міняємо refresh на нову пару → повторюємо запит.

**Гонка, яку треба закрити одразу.** Календар паралельно тягне заняття, блоки й налаштування.
Токен протух → усі три отримають 401 → усі три кинуться оновлювати. Двоє програють, і другий
refresh прийде вже використаним, а це в нашій схемі означає «крадіжка, гасимо сесію». Тренера
викине з додатка на рівному місці.

Тому оновлення серіалізується: перший оновлює, решта чекають на той самий проміс і
повторюються. Кілька рядків, без яких додаток розвалюється щоразу, коли екран завантажується
цілком.

### Офлайн-читання

Кеш Query зберігається в `AsyncStorage`, при старті піднімається з диска. Термін життя —
**7 днів**; старіше не показуємо, бо розклад двотижневої давнини гірший за чесне «немає даних».

Видно офлайн: розклад і календар, список клієнтів, картка клієнта, баланси, профіль.

**Позначка несвіжості обов'язкова** — смужка «Немає зв'язку. Дані станом на 14:30». Інакше
тренер проведе заняття, яке клієнт скасував годину тому.

### Зміни офлайн

Кнопки збереження неактивні, поруч «Потрібен зв'язок». Відмова **до** відкриття форми, а не
після натискання «Зберегти» — інакше тренер втрачає заповнену форму й довіру.

### Ключі кешу

```
['coach','sessions', {from, to}]   ['coach','blocks']      ['coach','settings']
['coach','clients']                ['coach','client', id]  ['coach','availableSlots', date]
['user','profile']                 ['notifications']
```

Після зміни заняття інвалідуються `['coach','sessions']` і `['coach','availableSlots']` —
створене заняття забирає слот. Прихід пуша інвалідує ті самі ключі й перепланує нагадування.

## 5. Перенесення календаря

`apps/web/app/coach/calendar/CalendarClient.tsx` — 1179 рядків, ~20 `useState`, 9 `fetch`,
5 модалок і 2 діалоги в одному файлі. Це 53% усього тренерського UI.

| Частина | ≈ рядків | Доля |
|---|---|---|
| Чисті функції-хелпери | 60 | переносяться як є |
| Стан і 9 `fetch` | 250 | замінюються Query-хуками |
| Сітка місяця + агенда дня | 250 | переписуються на RN |
| 5 модалок + 2 діалоги | 600 | переписуються на bottom sheets |

Доменна логіка вже написана й працює в RN без змін (`packages/core`). Усередині самого
компонента є ще `getMonthGrid`, `buildDayTimeline`, `isPastSlot`, `hoursForDate`,
`blockSummary` — їх треба витягти й перенести.

### Розкладка

```
app/(coach)/calendar/index.tsx    — місяць + агенда
components/calendar/
  MonthGrid.tsx      DayAgenda.tsx      SessionSheet.tsx
  StatusSheet.tsx    BlocksSheet.tsx    ScheduleSheet.tsx
hooks/
  useCalendarData.ts        useSessionMutations.ts
```

Один файл на 1179 рядків стає дев'ятьма по 100–200. Це не косметика: у поточному файлі важко
орієнтуватися, і кожна правка ризикує зачепити сусіднє.

**Веб-версію не чіпаємо.** Застосувати ту саму розкладку до `CalendarClient.tsx` — окрема
задача й окремий PR, якщо колись знадобиться.

### Ризик: таймзона під Hermes

`tz.ts` жорстко працює з Києвом і покладається на `Intl`. Hermes збирається з **урізаним ICU** —
набір таймзон може бути неповним. Якщо `Intl.DateTimeFormat` із `Europe/Kyiv` поведеться
інакше, ніж у браузері, поїдуть усі дати, і поїдуть тихо.

**Перевірка `tz.ts` під Hermes — перша задача етапу 1**, до будь-якого UI. Лікується
`jsc-intl` або Hermes із повним ICU, але знати треба на першому тижні.

## 6. Центр сповіщень

Пуш — подія без пам'яті: телефон вимкнений, сповіщення змахнули, користувач у вебі —
повідомлення втрачено. Центр сповіщень закриває цю дірку.

**Запис у базі — істина. Пуш — лише один зі способів доставки.** Усі вісім подій спершу
створюють запис, і вже потім летить пуш. Веб отримує ту саму стрічку без жодної
пуш-інфраструктури.

### Схема

`packages/db/src/schemas/notification.schema.ts`

```
userId       ObjectId → User, обов'язково
type         enum: session_booked | session_cancelled_by_client | session_created |
                   session_moved | session_status_changed | session_cancelled_by_coach |
                   coach_invite | balance_topped_up | daily_digest
title        String
body         String
data         Mixed — { sessionId, clientId } для переходу по кліку
collapseKey  String — той самий ключ, що в пуші
readAt       Date | null
expiresAt    Date
createdAt    через timestamps: true
```

Індекси: `{ userId: 1, createdAt: -1 }` (стрічка), `{ userId: 1, readAt: 1 }` (лічильник),
`{ expiresAt: 1 }` з `expireAfterSeconds: 0` — **місяць життя без cron**. Фоновий TTL-процес
Mongo прокидається приблизно раз на хвилину; для місячного терміну неточність неважлива.

Ролі виходять безкоштовно: усе фільтрується за `userId` із сесії. Тренер фізично не побачить
чужих — навіть підставивши чужий id, бо той у запиті не використовується.

### Одна точка входу

`apps/web/lib/notify.ts` замінює прямі виклики `sendPush`:

```ts
notify(userIds, { type, title, body, data?, collapseKey? })
```

Пише записи в базу, потім шле пуші. Вісім місць у роутах викликають `notify`.

**Згортання діє й тут.** Було б дивно, якби в шторці одне сповіщення, а в центрі — дванадцять
рядків. Той самий `collapseKey`: якщо непрочитаний запис із цим ключем уже є в межах години —
він оновлюється, а не дублюється.

Помилка відправки пуша не валить запит і не відкочує запис — запис важливіший за доставку.

### Роути

```
GET    /api/notifications?cursor=&limit=20   → { items, nextCursor, unreadCount }
PATCH  /api/notifications/[id]               → { read: true }
DELETE /api/notifications/[id]
POST   /api/notifications/read-all
```

Через `getAuthUser`, тобто один код і для cookie, і для Bearer. Це 3 файли `route.ts`
(`/`, `/[id]` з PATCH і DELETE, `/read-all`). Разом із трьома роутами входу файлів
`route.ts` у проєкті стає **29** проти нинішніх 23.
Пагінація курсорна: стрічка росте зверху, `skip` на ній працює неправильно.

### Веб

`apps/web/components/NotificationBell.tsx` — клієнтський острівець у шапці поруч із
`LogoutButton`, у `coach/layout.tsx` і клієнтському лейауті. **Іконка — дзвіночок.**

Будується з наявного: `Popover.tsx` для панелі, `Badge.tsx` для червоної крапки. Нових
компонентів у `packages/ui` не потрібно.

Пушів у вебі немає → лічильник опитується раз на 60 секунд і при поверненні фокусу на вкладку.
Запит іде по індексу `{ userId, readAt }`.

### Мобілка

Той самий дзвіночок у шапці, але панель — окремий екран, а не спливне вікно: стрічка за місяць
довга. Опитування не потрібне — прихід пуша інвалідує `['notifications']`. Плюс
`setBadgeCountAsync` малює число на іконці додатка.

### Прочитане й нове

Позначка **поіменна**, не гуртова:

- клік по рядку → позначається прочитаним **і** переходить на потрібний екран через `data`
- непрочитані візуально виділені, прочитані лишаються в стрічці
- червона крапка = є хоч одне непрочитане
- кнопка «Прочитати всі»
- видалення: свайп у мобілці, × у вебі

Відкриття панелі саме по собі прочитаним нічого не позначає — інакше поділ на «нові» й
«прочитані» зникав би в мить відкриття.

## 7. Тестування й доставка

### Поточний стан

26 тестових файлів на Vitest (node-середовище, `mongodb-memory-server`), 4 Playwright-специфікації.

> **Розбіжність:** CLAUDE.md описує пайплайн «PR → dev: lint + typecheck → Vitest → Playwright
> smoke → Vercel Preview», але `.github/workflows/` у репозиторії **немає**. CI зараз або
> ручний, або на боці Vercel.

### Що з наявними тестами

Шість файлів з `__tests__/lib/` переїжджають у `packages/core` разом із кодом і лишаються на
Vitest. Саме вони доводять, що перенесення нічого не зламало.

Роутові тести лишаються де є, але розширюються: кожен захищений роут має прийняти і cookie, і
Bearer, і відкинути протухлий токен. Один параметризований набір на хелпер плюс точкові перевірки.

### Нові тести на бекенді

- вхід через `/api/mobile/auth/login`, ротація refresh
- **повторне використання refresh гасить сесію** — правило безпеки, яке легко зламати
  рефакторингом і неможливо помітити руками
- `push.ts` у dev-режимі (лог замість відправки), видалення мертвих токенів
- згортання: другий пуш у серії без звуку, з правильним лічильником
- `notify`: оновлення непрочитаного запису замість дубля в межах години
- TTL і фільтрація за `userId` у роутах сповіщень

Усе лягає на наявний стенд із `mongodb-memory-server`.

### Мобілка

Vitest із React Native не дружить — стандарт Expo це Jest із пресетом `jest-expo`. Тобто в
монорепо з'являється **другий тестовий раннер**. Це реальна ціна, і уникнути її, крім як не
писати тестів на компоненти, не вийде.

Піраміда навмисно низька:

- логіка вже покрита в `packages/core` під Vitest — не дублюємо
- Jest точково: планувальник локальних нагадувань і оновлення токена з гонкою. 2–3 файли
- Maestro (YAML, без нативного тестового рантайму на відміну від Detox) — один димовий
  сценарій: вхід → календар → створення заняття → вихід

Причина скупості: мобільний UI на старті змінюватиметься щотижня. Цінність тестів на
компоненти з'явиться, коли екрани встояться.

### Expo Go — середовище розробки й приймання

**Рішення замовника: уся розробка й тестування відбуваються в Expo Go. Жодних платежів
Apple чи Google, доки додаток не прийнято в Expo Go. Перевірка віддалених пушів свідомо
відкладається.**

Документація Expo однозначна: *"You must use a development build to use push notifications
since the capability is not built into Expo Go."* Локальні сповіщення в Expo Go працюють.

| Спосіб | Що працює | Ціна |
|---|---|---|
| **Expo Go** | усе, крім віддалених пушів | безкоштовно |
| Dev build, **Android** | усе, включно з пушами | **безкоштовно** — APK ставиться напряму, Play Console не потрібен |
| Dev build, **iOS** | усе, включно з пушами | потребує $99 Apple |
| Стори | усе | $99/рік + $25 одноразово |

> $25 Google — це плата за Play Console, тобто за право публікувати. Для перевірки пушів на
> Android вона не потрібна.

### Що перевіряється в Expo Go попри відкладені пуші

- **Локальні нагадування про заняття** — вони не віддалені, тож працюють повністю. Головний
  клієнтський сценарій покритий.
- **Центр сповіщень цілком** — це API плюс UI. Записи створюються при кожній події, стрічка
  наповнюється, дзвіночок червоніє; та сама подія видна і у вебі, і в мобілці.
- **Логіка відправки** — `push.ts` у dev-режимі пише в консоль замість надсилання, як зараз
  робить `email.ts`. Кому, що й зі згортанням — видно в логах і покривається Vitest.

**Неперевіреним лишається доставляння на пристрій:** `collapseId`/`tag`, приглушення звуку
після першого пуша в серії, екран дозволів. Код пишеться й покривається юніт-тестами, але до
першого dev build у роботі його ніхто не бачив. Див. ризик 8.

### Стори — окремий платний трек

Запускається тоді, коли замовник вирішить, а не за розкладом розробки.

EAS Build збирає обидві платформи в хмарі — Mac не потрібен. EAS Submit відвантажує в App
Store Connect і Google Play.

**Почати рано в межах цього треку:** нові персональні акаунти Google Play проходять закрите
тестування з 12 тестерами протягом **14 днів** перед публікацією. Щойно трек стартує й
з'явиться збірка, яка запускається й дозволяє увійти, — виливаємо її в закритий трек і
збираємо 12 людей. Інакше в кінці доведеться чекати два тижні на порожньому місці.

iOS: TestFlight доступний одразу після оплати $99.

## Відомі ризики

1. **`tz.ts` під Hermes** — урізаний ICU може зламати київську таймзону тихо. Перевірка перша.
2. **Metro + pnpm symlinks** — `node-linker=hoisted` змінює розкладку для всього монорепо,
   включно з вебом.
3. **Винесення `packages/core`** — рух робочого коду, який імпортується з дев'яти місць.
4. **Гонка оновлення токена** — без серіалізації викидає користувача при кожному повному
   завантаженні екрана.
5. **Фонове пробудження iOS** — не гарантоване, тож ковзне вікно локальних нагадувань
   залежить від того, що додаток відкривають.
6. **14 днів закритого тестування Google** — календарний строк, який не можна прискорити.
   Стосується платного треку.
7. **Оплата Apple** — без неї пуші на iOS не перевірити взагалі. Для Android оплата
   не потрібна: dev build безкоштовний.
8. **Віддалені пуші пишуться неперевіреними.** За рішенням замовника розробка й приймання
   відбуваються в Expo Go, де віддалені пуші не працюють. Код `push.ts`, згортання через
   `collapseId`/`tag`, приглушення звуку й екран дозволів покриті юніт-тестами проти
   dev-режиму, але на живому пристрої не бачені. Найімовірніше місце сюрпризу — саме
   згортання: поведінка `collapseId` і `tag` різна на iOS та Android і на емуляторі не
   відтворюється. Закривається кроком П1 платного треку, який сам по собі безкоштовний.
